# Deployment boundary for the shared-container candidate

**No production deployment, SSH, owner-service restart or DNS/proxy/certificate change is authorized by the current implementation phases.** Local additive development migrations were separately authorized; they do not authorize a production change. Candidate 0.9.0 differs from the last recorded deployed 0.8.1. Do not apply current Compose to that live database without the separately approved [transition and recovery sequence](UPGRADE_ROLLBACK.md).

After approval, inventory the actual host OS/architecture, Docker/Compose, existing containers/listeners, available resources, Nginx includes/firewall/certificate tooling and other hosted-site responses. Port 18743 must be free or already confirmed as Shipping's own loopback binding. Do not infer current server state from historical records or this local build.

The intended production project remains `jahez-shipping-prod`, web `127.0.0.1:18743:8000` and internal Redis only. Named volumes remain `jahez-shipping-prod_shipping_data` and `_redis_data`; old Beat/private volumes are retained as recovery evidence and are not deleted. Current Compose has no worker or scheduler. Its default image is 0.9.0; release acceptance uses the separate `jahez-shipping-phase07:0.9.0` tag. The runtime runs UID 10001, readonly root/bounded tmpfs, dropped capabilities, bounded memory/logging and a 95-second grace period. Web has a 128-process limit and one CPU; Redis has a 64-process limit and half a CPU. Gunicorn uses one worker/two threads and a 30-second request timeout. These are configuration limits, not capacity benchmarks.

Fresh env creation is `python3 scripts/init_prod_env.py` (exclusive 0600, never overwrite). Existing env/Groq key/models and Django secret stay private/stable. Only cache Redis URL remains required; obsolete private carrier/broker values are ignored, not rewritten. Startup/preflight validate production host/origin/secret/cache/flags without printing values. `python3 scripts/preflight.py --running` inspects configuration without changing services; never display resolved Compose environments.

A new empty installation uses one-off `migrate --noinput`, `setup_roles` (no assignments), interactive `createsuperuser`, then web startup with Redis healthy. Existing-data activation must instead follow the guarded transition guide. Web never auto-migrates. Verify nonroot volume ownership, actual loopback binding, health, bilingual home/company and approved-code tracking states, retained admin login/CSRF/permissions and no retired endpoints. Protect other apps and current SSH/firewall access. Docker published ports can bypass firewall assumptions; rely on the actual loopback binding.

[Nginx/SSL](NGINX_SSL.md), [operations](OPERATIONS_RUNBOOK.md) and [backup/restore](BACKUP_RESTORE.md) describe retained controls. Production credentials, host inventory, access helpers and operational evidence belong outside Git/images. Do not publish old private history or copy dev data into production. No live provider, scheduling, off-server backup or deployment completion is inferred from isolated tests.

Phase 5 prepares a host systemd oneshot/timer outside Compose; it remains uninstalled/inactive until Phase 8. It uses Compose exec against the approved running Shipping web container, without creating a queue/service or starting other applications. [Review the scheduling prerequisites, configuration and removal procedure](OPERATIONS_RUNBOOK.md#prepared-linux-timer--activation-only-in-phase-8). Current deployment/systemd support is not inferred from local parsing or historical inventory.

Phase 6 source additionally requires `containers.0002_reviewed_public_tracking`. A release image and schema must match; do not point an older image at a changed schema or start new source before verifying its migration plan and backup. Existing publication flags do not create public snapshots. Review and confirm each intended first publication, and leave carrier auto-publication off unless the owner explicitly approves that journey. Production lookup counters require the shared Redis backend and the existing safe proxy log/referrer/cache controls. The Phase 7 verifier rehearses the built production image and matching model/private-file recovery in isolated synthetic storage. It does not authorize deployment or establish actual VPS capacity, HTTPS, live source access, backups or scheduled execution.
